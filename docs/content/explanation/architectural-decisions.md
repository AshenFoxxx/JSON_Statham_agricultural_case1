# Объяснение: Архитектурные решения

> **Тип:** Explanation (объяснение)
> 
> Цель: понять, почему проект устроен именно так.

---

## Почему FastAPI, а не Django?

### FastAPI

**Плюсы:**

- Высокая производительность (асинхронный)
- Автоматическая генерация документации (Swagger UI)
- Встроенная валидация через Pydantic
- Лёгкий фреймворк — только то, что нужно
- Подходит для микросервисов и API

**Минусы:**

- Нет встроенного ORM (нужен SQLAlchemy)
- Нет встроенного admin-панели
- Меньше готовых решений «из коробки»

### Django

**Плюсы:**

- Всё из коробки (ORM, admin, auth)
- Большое сообщество
- Много готовых приложений

**Минусы:**

- Тяжелее, медленнее
- Monolithic-архитектура
- Сложнее кастомизировать

**Вердикт:** FastAPI для API-сервера — быстрее, легче, лучше документация.

## Почему React, а не Vue или Angular?

### React

**Плюсы:**

- largest ecosystem в мире
- TypeScript-first
- Компонентный подход
- React Router для навигации
- Tailwind CSS отлично интегрируется

**Минусы:**

- Нужно много зависимостей (Router, State management)
- Flexibility может привести к хаосу

### Vue

**Плюсы:**

- Проще для новичков
- Всё из коробки
- Отличная документация

**Минусы:**

- Меньше экосистема
- Меньше вакансий

### Angular

**Плюсы:**

- Всё из коробки
- Строгая архитектура
- TypeScript по умолчанию

**Минусы:**

- Тяжёлый
- Крутая кривая обучения
- Overkill для проекта такого масштаба

**Вердикт:** React — самый популярный, лучшая экосистема, TypeScript-first.

## Почему PostgreSQL, а не MongoDB?

### PostgreSQL

**Плюсы:**

- Реляционная модель — идеально для связей (Product ↔ Order ↔ Buyer)
- ACID-транзакции
- SQLAlchemy ORM отлично работает
- SQL — стандарт де-факто
- Надёжность и стабильность

**Минусы:**

- Жёсткая схема (нужны миграции)
- Сложнее масштабировать горизонтально

### MongoDB

**Плюсы:**

- Гибкая схема
- Лёгкая горизонтальная масштабирование
- Document-oriented

**Минусы:**

- Нет связей (JOIN)
- Нет транзакций «из коробки»
- Сложнее обеспечить консистентность

**Вердикт:** PostgreSQL — данные структурированы, есть связи, нужна целостность.

## Почему Tailwind CSS, а не Bootstrap?

### Tailwind CSS

**Плюсы:**

- Утилитарный подход — полный контроль над стилями
- Нет конфликтов с готовыми компонентами
- Маленький размер production-бандла
- Dark mode «из коробки»

**Минусы:**

- Много классов в HTML
- Нужно привыкнуть

### Bootstrap

**Плюсы:**

- Готовые компоненты
- Быстрый старт

**Минусы:**

- Ограниченный кастомизация
- Большой размер
- Все сайты выглядят одинаково

**Вердикт:** Tailwind — полный контроль, современный подход, лучше для кастомного UI.

## Почему Vite, а Create React App?

### Vite

**Плюсы:**

- Молниеносный HMR (Hot Module Replacement)
- Современный сборщик на ESBuild
- Меньше конфигурации
- Быстрая сборка production

**Минусы:**

- Относительно новый (меньше плагинов)

### CRA

**Плюсы:**

- Всё из коробки
- Большое сообщество

**Минусы:**

- Медленный HMR
- Устаревает (Facebook объявил о deprecation)

**Вердикт:** Vite — быстрее, современнее, легче.

## Почему Docker Compose, а не Kubernetes?

### Docker Compose

**Плюсы:**

- Простой конфиг (YAML, ~30 строк)
- Локальная разработка
- Нет необходимости в кластере

**Минусы:**

- Нет auto-scaling
- Нет self-healing
- Один хост

### Kubernetes

**Плюсы:**

- Auto-scaling
- Self-healing
- Multi-node

**Минусы:**

- Сложность (Helm, manifests)
- Ресурсы (minikube ~2GB)
- Overkill для проекта хакатона

**Вердикт:** Compose для разработки, K8s для продакшена.

---

## Почему разделённые сервисы?

### Frontend + Backend + Database

**Почему разделены:**

- Разные языки (TypeScript vs Python)
- Разные зависимости
- Разные lifecycle (SPA vs API)
- Независимое масштабирование
- Разные команды разработки

**Почему не монолит:**

- Frontend не нужен для работы API
- Backend обновляется часто, frontend редко
- Разные циклы сборки и деплоя
