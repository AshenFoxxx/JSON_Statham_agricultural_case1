# Объяснение: Архитектурные решения

## Почему FastAPI, а не Django? {#fastapi}

### FastAPI

Плюсы:

- Высокая производительность (асинхронный);
- Автоматическая генерация документации (Swagger UI);
- Встроенная валидация через Pydantic;
- Легкий фреймворк — только то, что нужно;
- Подходит для микросервисов и API.

Минусы:

- Нет встроенного ORM (нужен SQLAlchemy);
- Нет встроенного admin-панели;
- Меньше готовых решений «из коробки».

### Django

Плюсы:

- Все из коробки (ORM, admin, auth);
- Большое сообщество;
- Много готовых приложений.

Минусы:

- Тяжелее, медленнее;
- Monolithic-архитектура;
- Сложнее кастомизировать.

Вердикт: FastAPI для API-сервера — быстрее, легче, лучше документация.

## Почему React, а не Vue или Angular? {#react}

### React

Плюсы:

- largest ecosystem в мире;
- TypeScript-first;
- Компонентный подход;
- React Router для навигации;
- Tailwind CSS отлично интегрируется.

Минусы:

- Нужно много зависимостей (Router, State management);
- Flexibility может привести к хаосу.

### Vue

Плюсы:

- Проще для новичков;
- Все из коробки;
- Отличная документация.

Минусы:

- Меньше экосистема;
- Меньше вакансий.

### Angular

Плюсы:

- Все из коробки;
- Строгая архитектура;
- TypeScript по умолчанию.

Минусы:

- Тяжелый;
- Крутая кривая обучения;
- Overkill для проекта такого масштаба.

Вердикт: React — самый популярный, лучшая экосистема, TypeScript-first.

## Почему SQLite, а не PostgreSQL? {#sqlite}

### SQLite

Плюсы:

- Файловая база — не требует отдельного сервиса;
- Нет настройки и администрирования;
- Идеально для прототипов и небольших проектов;
- Встроен в Python;
- Быстрее для read-heavy нагрузки.

Минусы:

- Нет сетевой поддержки;
- Ограничения для высокой нагрузки;
- Нет репликации.

### PostgreSQL

Плюсы:

- Реляционная модель — идеально для связей (Product ↔ Order ↔ Buyer);
- ACID-транзакции;
- SQLAlchemy ORM отлично работает;
- SQL — стандарт де-факто;
- Надежность и стабильность.

Минусы:

- Жесткая схема (нужны миграции);
- Сложнее масштабировать горизонтально;
- Требует отдельного сервиса.

Вердикт: SQLite для прототипа и хакатона — проще, быстрее, не требует настройки.

## Почему Tailwind CSS, а не Bootstrap? {#tailwind}

### Tailwind CSS

Плюсы:

- Утилитарный подход — полный контроль над стилями;
- Нет конфликтов с готовыми компонентами;
- Маленький размер production-бандла;
- Dark mode «из коробки».

Минусы:

- Много классов в HTML;
- Нужно привыкнуть.

### Bootstrap

Плюсы:

- Готовые компоненты;
- Быстрый старт.

Минусы:

- Ограниченный кастомизация;
- Большой размер;
- Все сайты выглядят одинаково.

Вердикт: Tailwind — полный контроль, современный подход, лучше для кастомного UI.

## Почему Vite, а не Create React App? {#vite}

### Vite

Плюсы:

- Молниеносный HMR (Hot Module Replacement);
- Современный сборщик на ESBuild;
- Меньше конфигурации;
- Быстрая сборка production.

Минусы:

- Относительно новый (меньше плагинов).

### CRA

Плюсы:

- Все из коробки;
- Большое сообщество.

Минусы:

- Медленный HMR;
- Устаревает (Facebook объявил о deprecation).

Вердикт: Vite — быстрее, современнее, легче.

## Почему Docker Compose, а не Kubernetes? {#docker-compose}

### Docker Compose

Плюсы:

- Простой конфиг (YAML, ~30 строк);
- Локальная разработка;
- Нет необходимости в кластере.

Минусы:

- Нет auto-scaling;
- Нет self-healing;
- Один хост.

### Kubernetes

Плюсы:

- Auto-scaling;
- Self-healing;
- Multi-node.

Минусы:

- Сложность (Helm, manifests);
- Ресурсы (minikube ~2GB);
- Overkill для проекта хакатона.

Вердикт: Compose для разработки, K8s для продакшена.

## Почему разделенные сервисы? {#razdelenie}

### Frontend + Backend

Почему разделены:

- Разные языки (TypeScript vs Python);
- Разные зависимости;
- Разные lifecycle (SPA vs API);
- Независимое масштабирование;
- Разные команды разработки.

Почему не монолит:

- Frontend не нужен для работы API;
- Backend обновляется часто, frontend редко;
- Разные циклы сборки и деплоя.

## Почему CP-SAT solver? {#cp-sat}

### OR-Tools CP-SAT

Плюсы:

- Решатель ограничений от Google;
- Доказывает оптимальность решения;
- Поддержка сложных ограничений;
- Максимизация прибыли, а не минимизация стоимости.

Минусы:

- Сложнее в настройке, чем базовый solver;
- Требует больше вычислительных ресурсов.

### Базовый solver

Плюсы:

- Простой;
- Быстрый.

Минусы:

- Не доказывает оптимальность;
- Ограниченные возможности оптимизации.

Вердикт: CP-SAT для задачи с множеством ограничений и целевой функцией максимизации прибыли.

## Почему OSRM? {#osrm}

### OSRM API

Плюсы:

- Реальные дороги, а не прямые линии;
- Точные расстояния и время в пути;
- Бесплатный публичный API;
- Учитывает тип дороги и ограничения.

Минусы:

- Требует интернет;
- Зависимость от внешнего сервиса.

### Гаверсинус

Плюсы:

- Работает офлайн;
- Не требует внешних сервисов.

Минусы:

- Неточные расстояния (прямые линии);
- Не учитывает дороги.

Вердикт: OSRM для точных расчетов по реальным дорогам.
