# Бэкенд: план поставок

Документ для фронтенда и его ИИ-ассистента. Бэкенд уже считает план. Фронт отправляет текущие данные формы и рисует ответ. Считать оптимум на клиенте не нужно.

## Кто что делает

Бэкенд принимает культуры, заказы покупателей и машины, строит план с максимальной прибылью и возвращает отгрузки, рейсы и деньги.

Фронт:

1. Даёт ввести или изменить эти данные. Для старта формы можно взять `GET /api/v1/demo`.
2. По кнопке «Рассчитать поставки» отправляет **текущее состояние формы** на `POST /api/v1/plan`.
3. Показывает таблицу отгрузок, рейсы, выручку, транспортные затраты, прибыль, остатки и потери.
4. Даёт поменять вход и нажать расчёт снова. Отдельного эндпоинта пересчёта нет: это тот же `POST` с новым JSON. Так закрывается демо, где одну машину помечают недоступной или меняют цену.

Имена (`name`) показываются человеку. Связка строк в ответе идёт по `id`, которые задаёт фронт.

## Запуск

Из папки `backend`:

```powershell
.venv\Scripts\python -m uvicorn app.main:app --reload
```

Базовый адрес: `http://127.0.0.1:8000`. Схема запросов: `http://127.0.0.1:8000/docs`. CORS открыт для любого origin.

## Эндпоинты

| Метод | Путь | Зачем |
| --- | --- | --- |
| `GET` | `/health` | Проверка, что сервер жив. Ответ: `{"status": "ok"}`. |
| `GET` | `/api/v1/demo` | Пример тела запроса, чтобы заполнить форму. Сам по себе план не считает. |
| `POST` | `/api/v1/plan` | Единственный расчёт. Тело — данные формы. |

## Тело `POST /api/v1/plan`

```json
{
  "products": [
    {
      "id": "strawberry",
      "name": "Клубника",
      "stock_kg": 600,
      "max_delivery_hours": 6
    }
  ],
  "buyers": [
    {
      "id": "buyer-kaluga",
      "name": "Сеть Калуга",
      "travel_time_hours": 4,
      "orders": [
        {
          "product_id": "strawberry",
          "demand_kg": 250,
          "price_per_kg": 210
        }
      ]
    }
  ],
  "vehicles": [
    {
      "id": "vehicle-a",
      "name": "Газель А",
      "capacity_kg": 800,
      "cost_per_trip": 6000,
      "max_trips": 1,
      "available": true
    }
  ]
}
```

Поля:

- `products` — минимум одна культура. `stock_kg` и `max_delivery_hours` больше 0. Лимит часов — только время в пути, не срок хранения на складе.
- `buyers` — минимум один покупатель, у него минимум один заказ. `travel_time_hours` ≥ 0. В заказах одного покупателя `product_id` не повторяется. `demand_kg` > 0, `price_per_kg` ≥ 0.
- `vehicles` — минимум одна машина. `capacity_kg` > 0, `cost_per_trip` ≥ 0, `max_trips` от 1 до 10. `available: false` означает, что машина сломана и в план не войдёт.
- `id` культур, покупателей и машин уникальны внутри своего списка. Каждый `product_id` в заказе должен совпадать с `id` культуры.

Неверное тело отвечает `422` и JSON с полем `detail`. План в этом случае не считается.

Полный рабочий пример без сокращений: `GET /api/v1/demo`.

## Ответ `POST /api/v1/plan`

`status`:

- `optimal` — план построен;
- `infeasible` — допустимого плана нет;
- `not_solved` — решатель не закончил расчёт.

`objective` сейчас всегда `maximize_profit`.

Деньги в рублях:

- `revenue` — сумма `quantity_kg * price_per_kg` по отгрузкам;
- `transport_cost` — сумма `cost` по рейсам;
- `profit` — `revenue - transport_cost`.

`shipments` — строка поставки: культура, покупатель, машина, килограммы. Несколько рейсов одной машины к одному покупателю с одной культурой уже сложены в одну строку.

`trips` — один рейс: машина, покупатель, стоимость этого рейса, загрузка в кг. Один рейс везёт одному покупателю. Загрузка не больше `capacity_kg`.

`balances` — по каждой культуре из запроса:

- `shipped_kg` — сколько уехало;
- `leftover_kg` — `stock_kg - shipped_kg`, не уехало из-за спроса или нехватки машин;
- `loss_kg` — сколько килограммов нельзя доставить ни одному покупателю в срок даже при свободном транспорте. Это часть остатка, отдельная цифра.

`assumptions` — готовый текст допущений. Его можно показать на экране как есть.

`message` — короткая строка для статуса расчёта, не замена таблицам.

## Как устроен расчёт

Это нужно, чтобы подписи на экране не обещали лишнего.

Прибыль максимизируется. Культуру нельзя везти покупателю, если `travel_time_hours` больше `max_delivery_hours`. Отсчёт срока начинается в момент отправки. Время на складе, момент сбора и очередь рейсов одной машины не моделируются. Вместимость — в килограммах. Машина с `available: false` пропускается.

Карты, пробки, склад и ERP бэкенд не делает. Для демо достаточно формы, кнопки расчёта и экрана результата. Смена цены или поломка машины — правка JSON и повторный `POST`.
