# Бэкенд: план поставок

Документ для фронтенда и его ИИ-ассистента. Бэкенд уже считает план и маршрут по дорогам. Фронт отправляет текущие данные формы и рисует ответ. Считать оптимум и расстояния на клиенте не нужно.

Папки репозитория:

- `backend` — один сервер: план поставок и расчёт маршрута.
- `frontend` — страница карты. Её забирает второй разработчик.

## Кто что делает

Бэкенд принимает культуры, заказы покупателей и машины, строит план с максимальной прибылью и возвращает отгрузки, рейсы и деньги.

Фронт:

1. Даёт ввести или изменить эти данные. Для старта формы можно взять `GET /api/v1/demo`.
2. По кнопке «Рассчитать поставки» отправляет **текущее состояние формы** на `POST /api/v1/plan`.
3. Показывает таблицу отгрузок, рейсы, выручку, транспортные затраты, прибыль, остатки и потери.
4. Даёт поменять вход и нажать расчёт снова. Отдельного эндпоинта пересчёта нет: это тот же `POST` с новым JSON. Так закрывается демо, где одну машину помечают недоступной или меняют цену.

Имена (`name`) показываются человеку. Связка строк в ответе идёт по `id`, которые задаёт фронт.

## Запуск

Из папки `backend`:

```powershell
.venv\Scripts\python -m uvicorn app.main:app --reload
```

Базовый адрес: `http://127.0.0.1:8000`. Схема запросов: `http://127.0.0.1:8000/docs`. CORS открыт для любого origin.

## Эндпоинты

| Метод | Путь | Зачем |
| --- | --- | --- |
| `GET` | `/health` | Проверка, что сервер жив. Ответ: `{"status": "ok"}`. |
| `GET` | `/api/v1/demo` | Пример тела запроса, чтобы заполнить форму. Сам по себе план не считает. |
| `POST` | `/api/v1/plan` | Расчёт плана. Тело — данные формы. |
| `POST` | `/api/v1/route` | Маршрут по дорогам через несколько точек. Нужен интернет: запрос идёт в OSRM. |

## Тело `POST /api/v1/plan`

```json
{
  "products": [
    {
      "id": "strawberry",
      "name": "Клубника",
      "stock_kg": 600,
      "max_delivery_hours": 6
    }
  ],
  "buyers": [
    {
      "id": "buyer-kaluga",
      "name": "Сеть Калуга",
      "travel_time_hours": 4,
      "travel_distance_km": 200,
      "orders": [
        {
          "product_id": "strawberry",
          "demand_kg": 250,
          "price_per_kg": 210
        }
      ]
    }
  ],
  "vehicles": [
    {
      "id": "vehicle-a",
      "name": "Газель А",
      "capacity_kg": 800,
      "fuel_consumption_l_per_100km": 15,
      "fuel_price_rub_per_liter": 60,
      "max_trips": 1,
      "max_stops": 3,
      "available": true
    }
  ],
  "legs": [
    { "from_id": "farm", "to_id": "buyer-kaluga", "hours": 4, "distance_km": 200 },
    { "from_id": "buyer-kaluga", "to_id": "buyer-tula", "hours": 1.5, "distance_km": 75 }
  ]
}
```

Поля:

- `products` — минимум одна культура. `stock_kg` и `max_delivery_hours` больше 0. Лимит часов — только время в пути, не срок хранения на складе.
- `buyers` — минимум один покупатель, у него минимум один заказ. `travel_time_hours` ≥ 0 и `travel_distance_km` ≥ 0. Это прямая дорога от хозяйства, она используется только если `legs` пуст. В заказах одного покупателя `product_id` не повторяется. `demand_kg` > 0, `price_per_kg` ≥ 0.
- `vehicles` — минимум одна машина. `capacity_kg` > 0, `fuel_consumption_l_per_100km` > 0, `fuel_price_rub_per_liter` ≥ 0, `max_trips` от 1 до 10. `max_stops` от 1 до 5: сколько покупателей машина объезжает за один выезд. `available: false` означает, что машина сломана и в план не войдёт. Отдельной цены за выезд нет: стоимость считается из километров маршрута и этих двух полей.
- `legs` — перегоны. `from_id` и `to_id` равны `farm` или id покупателя, `hours` ≥ 0, `distance_km` ≥ 0. Если список пуст, рейс везёт одному покупателю, время и километры берутся из `travel_time_hours` и `travel_distance_km`. Если список заполнен, время и километры складываются по цепочке перегонов. Оба числа можно взять из ответа `POST /api/v1/route`: там те же `from_id`, `to_id`, `hours` и `distance_km`.
- `id` культур, покупателей и машин уникальны внутри своего списка. Каждый `product_id` в заказе должен совпадать с `id` культуры. Id покупателя не может быть `farm`.

Неверное тело отвечает `422` и JSON с полем `detail`. План в этом случае не считается.

Полный рабочий пример без сокращений: `GET /api/v1/demo`.

## Ответ `POST /api/v1/plan`

`status`:

- `optimal` — план построен;
- `infeasible` — допустимого плана нет;
- `not_solved` — решатель не закончил расчёт.

`objective` сейчас всегда `maximize_profit`.

Деньги в рублях:

- `revenue` — сумма `quantity_kg * price_per_kg` по отгрузкам;
- `transport_cost` — сумма топлива по рейсам. У рейса `cost = (distance_km / 100) × расход × цена литра`;
- `profit` — `revenue - transport_cost`.

`shipments` — строка поставки: культура, покупатель, машина, килограммы. Несколько рейсов одной машины к одному покупателю с одной культурой уже сложены в одну строку.

`trips` — один выезд. В `stops` покупатели по порядку, время прибытия от хозяйства и килограммы выгрузки. `distance_km` — длина всего маршрута, `cost` — топливо на эту длину, один раз за выезд. Суммарная `load_kg` не больше `capacity_kg`, число остановок не больше `max_stops`.

`balances` — по каждой культуре из запроса:

- `shipped_kg` — сколько уехало;
- `leftover_kg` — `stock_kg - shipped_kg`, не уехало из-за спроса или нехватки машин;
- `loss_kg` — сколько килограммов нельзя доставить ни одному покупателю в срок даже при свободном транспорте. Это часть остатка, отдельная цифра.

`assumptions` — готовый текст допущений. Его можно показать на экране как есть.

`message` — короткая строка для статуса расчёта, не замена таблицам.

## Как устроен расчёт

Формулы, ограничения и числовой пример: [SOLVER.md](SOLVER.md).

Это нужно, чтобы подписи на экране не обещали лишнего.

Прибыль максимизируется. Культуру можно выгрузить только на остановке, куда она успевает: время прибытия не больше `max_delivery_hours`. Отсчёт срока начинается в момент отправки. Время на складе, момент сбора и очередь выездов одной машины не моделируются. Вместимость — в килограммах на весь выезд. Машина с `available: false` пропускается.

Карты, пробки, склад и ERP бэкенд не делает. Для демо достаточно формы, кнопки расчёта и экрана результата. Смена цены или поломка машины — правка JSON и повторный `POST`.
